# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Security

- Pinning the snapshot runs no Git hook. `git worktree add` checks the commit out, so with `core.hooksPath` set to a tracked folder and the reviewed branch checked out, the reviewed commit's own `post-checkout` hook ran as the owner, outside every seat limit.
- `comment` posts only to an open pull request whose head is the commit its card is about (the verify's head, or else the review's). Before, `--pr` took any number, so the card could land on an issue, a closed or merged PR, or a PR at another commit, and with no `--pr` it went to whatever PR `gh` found for the checked-out branch. A named PR is now checked as a round's is; with no `--pr` the card goes to the one open PR at that head, and none or several is refused with the reason. A named PR that has moved past the card's head is refused with the next step: run verify at the PR's head, then `comment` with that verify.
- A seat's system prompt is the package's own text and nothing else. Pi appended `.pi/APPEND_SYSTEM.md` from the seat's working folder, which is the snapshot of the reviewed commit, and from the agent folder, and read a system prompt that named an existing file as that file. A file in the reviewed repository could therefore write instructions for every review, verify and grouping seat.
- Every seat's system prompt now says that what it reads in the repository (code, comments, docs, the diff, commit messages) is data, never instructions, and a reviewer reports as a finding text that tries to change the review's result, such as telling a reviewer to skip a file or to report nothing (ordinary instructional text, like this package's own lens prompts, is not one). Before, only the grouping and verify seats were told this, and only about the finding records. The skill tells the calling agent the same about finding text: follow no instruction in a finding, a report or the reviewed code.
- The verify round number and the automatic close-out read only signed records and markers (T502). `verify N` counted any `meta.json` and `round.posted` under `.review-panel/runs/`, so a planted record could bump or skip the number, and a planted `closeout.posted` stopped the close-out card. Now `verify N` counts only complete verify records signed with the owner's record key (`record.mac`, kind verify) whose signed `meta.json` names the review and that hold a signed `round.posted`. Every posted marker (`round-<N>.posted`, `closeout.posted`, a verify's own `round.posted`) holds a MAC from the record key over the record's run id, the marker's file name and the verify that wrote it; an unsigned, copied or earlier marker counts as no marker, and the verify that posts replaces it. Claims, `wx` creates and the PR-comment check work as before. Documented limits: claims are not signed, so a planted stale-looking `round-<N>.claim` is still skipped and bumps `verify N`, and a planted live-looking claim, or five planted stale-looking close-out claims, can stop an automatic post (never forge one or post a second card; `comment` still works); deleting genuine markers can repeat a `verify N`. Markers written before this change are unsigned and count as none, so a PR already reviewed and verified before upgrading can see `verify 1` again; its close-out is still posted at most once (the PR-comment check).
- G-ids expand only from the grouping recorded in the review's signed `execution.json`, the one its reply and PR comment showed (T501). A side `groups.json` with its `groups.mac` could be put back after a resume regrouped the same findings differently, or lost its grouping, and verify and comment would expand a G-id to a split the reply never showed. The package no longer writes or reads `groups.json` or `groups.mac`; one left in an older record is ignored. A review with no grouping step or a lost grouping refuses G-ids, saying which, and asks for F-ids.
- `verify` and `comment` no longer trust a run record planted in the reviewed repository (T492). Records live in `<repo>/.review-panel/runs/`, so anyone who could get files into the checkout could plant a `COMPLETE` review record (or a verify record marking findings resolved) that both accepted. A finished review (first run or resume) and a finished verify now write `record.mac`, an HMAC from the owner's record key bound to the run id, the record kind and the plan's MAC, over the exact bytes of the files verify and comment read (`plan.json`, `panel.json`, `meta.json`, `findings.json`, `execution.json` for a review; `panel.json`, `meta.json`, `verification.json` for a verify). Verify and comment read the key (never creating it) and take a record only when its `plan.mac` and `record.mac` check out; they parse only those signed bytes. An unsigned record, one signed with another key, a signed record copied to another run id, or a signed file copied in from another run is refused before any seat runs and before anything is posted, with the fix: run a new review. A missing or unusable key refuses the same way, now also for calls that name only F-ids. **Records written before this change are not signed and are refused: run a new review.** The seal covers the bytes the run itself wrote (kept as each file is written; a resume takes the `plan.json` bytes whose `plan.mac` it checked), never what is in the folder at the end, so a covered file a repository writer replaces while the seats run is not signed and is refused. Resume now rewrites `panel.json` from the signed plan, so a resumed review is signed too. Verify builds the automatic close-out card, and checks G-ids, from the review bytes it authenticated before any seat ran. Review and resume reply and post the findings the run stamped, never `findings.json` read back after the seal. A prior record behind a symlinked `.review-panel` or `runs` folder, or whose `meta.json` names a base or head that is not a commit in this repository (a signed record copied from another repository), is refused; a record from another clone of the same repository still passes, and a shallow checkout without the base commit refuses the owner's own record.

### Added

- Setup without Pi (T506). `review-panel auth providers` lists every provider, how it logs in (`account`, `API key`, both, or `none` for one set up by an environment variable or `models.json`) and whether it is logged in now, in the agent folder in use (`--json` too). `review-panel models [<provider>] [--search <text>] [--all] [--extension <path>] [--json]` lists the models the logins give, from the bundled SDK's own catalog without asking any provider: one row each with the exact `provider` and `model` ids, the context window, the output limit, thinking and images, then a ready-to-copy roster row. It loads each installed extension package, and each `--extension` file, on its own as a seat does, lists only the providers that package registered, and names the package's entry paths in the roster row's `extraExtensionPaths`; a package that fails or takes over 30 seconds to load is named and the rest is still listed. `review-panel extension install <source>`, `extension list [--json]` and `extension remove <source>` install, list and remove a Pi package (`git:`, `npm:` or a local folder) in the agent folder with the bundled SDK's own package manager, the code behind `pi install`, so it lands where Pi puts it, and print the extension entry paths to put in `extraExtensionPaths`. Only the agent folder's own `settings.json` is read; a repository's `.pi/` folder is never listed or loaded. In Pi's own folder (`~/.pi/agent`) install and remove change Pi's packages too, and the output says so. `extension install` decides on what Pi's own package manager parses from a source and refuses one that carries a credential (a password, any user name on an `http(s)://` URL, any SSH user other than `git`, user info in a scheme-less `git:` source however it is spaced, cased or ported), a percent-encoded host, any query on a git source or a ref that is not a plain name, and a scheme Pi cannot read. `npm:` installs registry packages only (`npm:<name>` or `npm:<name>@<version, range or tag>`): URL, `git+`, `git:`, `github:`, `file:`, alias and path npm specs are not supported (use `git:git@host:owner/repo`, or a registry token in `.npmrc`). because Pi would keep the credential in `settings.json` and in the clone folder's name and git would print it; use a git credential helper, an SSH source or an npm token in `.npmrc`. Branch refs with a slash (`@release/1.0`) install. review-panel's own output also hides the credential of a source recorded earlier (`***`, with a note that such paths cannot be copied), never changes a local path holding an `@`, and `extension remove` takes the redacted form `extension list` prints; git's and npm's own output passes through unchanged, which the refusal protects. git runs with `GIT_TERMINAL_PROMPT=0` (SSH can still prompt); the first Ctrl-C ends any setup command, and an install stopped that way exits at once, says whether `settings.json` listed the source when checked, and points to `extension list` for the final state. `models` loads each extension entry on its own, so the roster row names only the entry that registers the provider, and when a named provider is missing it lists the packages that failed or did not finish loading. A local source takes `~` and `file:` URLs; `git@host:owner/repo` needs the `git:` prefix. One provider's failing or hanging login check marks only its own row in `auth providers`, whose checks run side by side within 15 seconds each. `docs/configuration.md` walks through the whole setup without Pi. The skill does not run `extension install` or `extension remove` unless the owner asks.

- A review can group findings that describe the same defect. The owner config takes an optional `defaults.consolidator`, one roster id (validated like `defaults.verifySeats`, and named by `diagnose` when invalid). When it is set and a review submits two or more findings, one grouping seat runs after every reviewer has settled, on the same snapshot, within the seat budget, with the read-only tools, the package-owned `grouping` prompt and one submit tool, `submit_groups`. It reads every stamped finding as data and submits groups of F-ids; a submission with an unknown, missing or repeated id is refused and the seat may submit again. Grouping never drops, rewrites or re-rates a finding. The reply, `report.md` and the PR review comment show `G-1`, `G-2`, … (ordered by the highest severity a seat stated, then the lowest member F-id): a header with that severity and the lowest member's title, then each member's F-id, severity, own title, seat, place and evidence; a group of one is one row with both ids. A group too long for the PR comment posts its header and the members that fit, then a line counting the rest (all are in `report.md`), and the groups after it still post; a reply cut inside a group says so. The summary line reads `8 findings in 5 groups`, and the Seats line names the grouping seat. Group size is never shown as agreement or used to rank. `findings.json` is unchanged; `execution.json` records the grouping seat and its groups under `grouping`, signed with the rest of the record in `record.mac`. A failed, invalid or timed-out grouping keeps the flat list and adds `Lost: grouping (<roster id>, <class>)`. `verify` (`keptFindingIds`, `dismissed`, `lowAdvisory`) and `comment` accept G-ids as well as F-ids; a G-id expands to its members before any seat runs, and only from the grouping in the review's signed `execution.json` when it groups every F-id once, otherwise G-ids are refused with a request for F-ids. A list that names one F-id twice, such as a G-id and one of its own members, is refused. Resume runs the grouping step again over the final list. Without `defaults.consolidator` nothing changes. The skill now says findings may arrive grouped, to judge each group, and to pass G-ids or F-ids to verify.

- The owner config takes an optional `defaults.verifySeats`: one or two roster ids, no repeats, that run `verify`. Without it, verify runs the first `defaults.seats` entry, as before; a caller's `seats` (CLI `--seats`) still wins. An invalid value (not an array, empty, more than two, a repeat, an empty or non-string entry, or an id not in the roster) refuses the config, and `diagnose` names the field and the problem. The `review-panel` skill now tells the agent to omit `--seats` on verify so the owner's choice applies.
- Review and verify post each round to the open pull request, by default. When a run's head commit is the head of exactly one open PR (found with `gh api repos/{owner}/{repo}/commits/<head-oid>/pulls`, or named with `pr` / `--pr`), the review posts a new `## Review panel · review` comment (the reply's content without the local record path, the run ids in a hidden marker at the end), and each verify posts `## Review panel · verify N`: each kept id resolved, still present or inconclusive with the panel's evidence, each dismissed id with its reason, the low/advisory ids, and the regressions. A verify where every verify seat voted, each marked every kept id resolved (a kept finding of any severity counts as fixed), and none reported a regression also posts the close-out card (since T507 only with `--close-out` and nothing left open; see Changed) as a separate `## Review panel · close-out` comment, at most once per review (an exclusive claim in the review's run record stops a second or concurrent verify; set aside: a crash after GitHub accepted the card but before `closeout.posted` was written, which the PR-comment check catches, and a live verify whose claim looks stale to another, paused over 65 s mid-post, a clock over 65 s behind, or a container sharing the hostname, which can post a second card); otherwise the reply says why, such as `seats disagree on F-2` or `lost verify coverage`. `verify N` counts only earlier verifies whose comment reached the PR. An explicit `pr` must be open with the run's head as its head. Every post is a new comment; none is edited or deleted. Resume never posts. `prComment: false` (CLI `--no-pr-comment`) turns posting off for one run, and the owner config's new `defaults.prComment` (`"auto"`, the default, or `"ownerApproved"`) can require `ownerApproved: true` (CLI `--owner-approved`) for every post. No PR, more than one, or a missing, signed-out or failing `gh` posts nothing and ends the reply with one line saying why; a post never fails the run or changes an exit code. Every posted body, including the manual `comment` card, goes through one sanitizer: seat text, reasons and refs are plain text on one line, with only what can form Markdown or HTML backslash-escaped, and with a zero-width joiner after every `@`, `＠` and `#` and in `GH-123` and `://`, the dot of every `www.` backslash-escaped, and control, bidi and invisible characters replaced (an emoji keeps its presentation selector); file names and ids are code spans that cannot be closed early, with nothing escaped or joined inside. Bodies, the manual card's too, are cut by whole rows below GitHub's 65,536-character limit and go to `gh` on stdin; `gh` runs asynchronously within a per-round deadline, an interrupt kills a running `gh`, and comment listings read every page. Each verify claims its round number with an exclusive create of `round-<N>.claim` in the review's run record and checks `round-<N>.posted` again after the create, so two verifies never hold the same `verify N` at once, and a failed post gives its number back (a POST that `gh` reports as failed after GitHub accepted it can therefore repeat its number; that case is set aside). A waiting verify stops waiting while 30 s of the round deadline remain and then posts no round, saying so. No claim is ever taken over, renamed or put back: a claim left by a crash (older than 65 s, or made on this host by a process that is gone; a claim from another host is judged by age alone) stays where it is and is skipped, so a crash can leave a gap in the verify numbering, never a duplicate. The close-out is claimed with `closeout.claim-1`, `-2`, … (at most five): a stale generation sends the verify to the PR's comments and then to the next generation, only a generation's creator posts, and a posted card writes `closeout.posted`, which stops every later verify. A code span with nothing visible in it posts as `(empty)`. An invalid `defaults.prComment` now names the field and its allowed values in the readiness report, and a config that is not JSON or sits inside the repository gets a message naming that problem. Verify takes `dismissed` (`--dismissed`) and `lowAdvisory` (`--low-advisory`), checked against the review record before any seat runs. The `comment` action stays as the manual, owner-approved close-out card. Both test suites put a failing fake `gh` first on PATH, so no test can reach GitHub.

- A new `suggest` action (`{"action":"suggest","base":"main","head":"HEAD"}`, or `review-panel suggest --base main --head HEAD`) shows the lenses the diff's rules suggest before any seat runs, each with its reason and evidence, and marks lenses already in the owner's `defaults.lenses` as already on. It runs no seat, checks no login, never touches the record key, and resolves `base` and `head` with review's refusals. The tool still never adds a lens by itself: the `review-panel` skill now calls `suggest`, chooses the lenses with a reason for each, and passes them to `review` as `lenses`.
- Review, verify and resume replies, and each review `report.md`, carry a `Seats:` line that groups the seats by lens in planned order, for example `Seats: holistic (sol, opus), tests (sol, opus)`. Failed seats are listed there too, and still named on the `Lost:` line.
- A review writes each seat's outcome to its run record as soon as that seat settles, so a killed or crashed run keeps the seats it already paid for.
- A new `resume` action (`{"action":"resume","priorRunId":"<run-id>"}`) finishes an interrupted review record: it pins the same head commit, runs only the seats with no settled outcome, takes seat and lens names from the record but rebuilds each seat from the owner config and the package's prompts (a seat that cannot be rebuilt is lost coverage), and writes the report as a normal run would. The report names the seats it ran again. Verify runs, complete runs, and runs from earlier versions are refused. Resume treats the record as untrusted: it never follows a symlink in it or waits on a FIFO, refuses symlinked record folders and plans over the panel caps or holding control characters, re-runs any seat whose file does not match the outcome schema, checks every planned seat (settled or not) against the owner config, rebuilds a kept seat's prompt, extension paths and replay input instead of copying them, does not pass the record's scoping note to seats, runs the readiness check first, and takes the run lock before re-reading the record. The run lock is published whole (temp file, then a hard link; on a filesystem without hard links, such as FAT, written in place with an exclusive create), and a lock that names no pid is refused as one still being written, never taken over. Whether a record is a review comes from its signed plan, so a review whose base is named `verify` resumes.
- Review records are signed with the owner's record key, 32 random bytes in `record-key` beside the owner config (created on first use with mode `0600`, never in the repository). `plan.mac` is an HMAC of the exact `plan.json` bytes bound to the run id; each `seats/<n>.mac` binds the seat file's bytes to the run id, the plan MAC and the seat index. Resume refuses an unsigned plan, and re-runs any seat whose file is unsigned or forged, so a record planted in the repository cannot pass as panel coverage.
- Review and resume refuse to start when the record key is unusable: a key that is a symlink, not a regular file, readable by group or other users, owned by another user (where Node has `process.getuid`), or not 32 bytes; a key folder writable by other users; or a folder where the key cannot be created (resume never creates the key, so it also refuses when there is none). A key folder only its group can write (the `umask 002` default on Fedora, RHEL, Debian and Ubuntu) is accepted; `diagnose` shows it as a warning that keeps readiness. The fix text suggests `chmod go-w` only for a folder you own that is not sticky, and otherwise a config in a folder you own. `diagnose` checks the key the same way without creating it, and reports one `record key <path>` row with the cause and the fix. `docs/configuration.md` lists each cause with its fix. A run interrupted between writing `plan.json` and `plan.mac` is refused as interrupted, not as unsigned.
- Every run starts by removing this repository's leftover `review-panel-snapshot-*` worktrees whose owning process has exited, each by its exact path. A live run's snapshot, and any other worktree, is never touched; there is no repository-wide `git worktree prune`. Each snapshot sits in a private `0700` holder folder with its `owner.json`, created exclusively and never through a symlink. The sweep touches only folders the current user owns directly in the temp folder, never follows a symlink, and trusts an owner file only when this user owns it and its holder; a file planted in a shared `/tmp` authorizes nothing.
- The `review-panel` command. It runs the panel from a terminal or from any coding agent, with the actions `diagnose`, `suggest`, `review`, `verify`, `resume` and `comment`, plus `call '<json>'` for one action's whole argument object, flags named after the argument names, and no `--provider` or `--model` flags. It bundles Pi SDK 1.5.2 and reuses your Pi logins when `~/.pi/agent` has `auth.json` or `models.json` (or `PI_CODING_AGENT_DIR` names a folder); otherwise it keeps its own logins in `~/.pi-review-panel/agent`. `auth login <provider>` signs in with the account (OAuth, including subscriptions) or, with `--api-key`, saves a key read from stdin or a hidden prompt; `auth logout` and `auth status` complete the set. The report goes to stdout and progress to stderr; exit codes are 0 (completed), 1 (refused or failed) and 2 (usage) and never say whether there are findings. See `docs/cli.md`. Ctrl-C aborts the command, including while it waits on stdin. An error about an unknown command, option or argument, a provider id, or an unknown argument name in a `call` object repeats it only when it is shaped like a name (letters, no digits), in case it is a key typed in the wrong place. Values given on purpose can still appear in an error: the value of any flag, and any value in a `call` object, such as `repository` or `priorRunId`.
- `review-panel skill install [--agent claude,codex,grok,pi] [--dry-run] [--force]` links the package's one skill into each coding agent's personal skills folder: Claude Code (`$CLAUDE_CONFIG_DIR/skills`, default `~/.claude/skills`), Codex (`$CODEX_HOME/skills`, default `~/.codex/skills`), Grok (`$GROK_HOME/skills`, default `~/.grok/skills`) and Pi (`$PI_CODING_AGENT_DIR/skills`, default `~/.pi/agent/skills`). An agent counts when its home folder exists, and nothing is created for an absent agent unless `--agent` names it. A `review-panel` entry that is not this package's link is replaced only with `--force`. On Windows the skill is copied with a version stamp instead. `review-panel skill uninstall` removes only this package's own link or copy. An old `pi-review` skill gets a hint to remove it and is never deleted. `review-panel diagnose` lists the skill's state in each agent: linked, not installed, a broken or foreign link, or a stale copy.
- One `review-panel` skill (`skills/review-panel/SKILL.md`) for every coding agent: Claude Code, Codex, Grok and Pi. The agent runs the `review-panel` command itself: `diagnose`, then `suggest`, chooses the lenses with a reason for each, `review`, judges each finding keep or skip, and after committed fixes `verify` with the kept ids; `resume` for an interrupted run, and `comment --owner-approved` only after the owner says yes. It never starts another agent session, never names seats, and never treats exit 0 as a pass.

### Changed

- **Breaking: verify rounds chain, and the close-out card is posted once, at the end, only when asked (T507).** The first verify still takes the review's run id; every later verify takes the latest verify's run id (`--prior-run-id <latest verify>`), diffs from that verify's head, and checks only what is still open after it: its still-present (or inconclusive, or unanswered) ids and the regressions any round reported. Leave out `--kept-finding-ids` to check every open id, or name part of it; an id an earlier round resolved, dismissed or left as low/advisory is refused, and so is a verify against the review, or against an older verify, once a newer one exists (the refusal names the latest). Regressions get chain-stable ids, `V<link>-R<n>` (`V1-R1`), numbered across the verify's seats (two seats both stamped `regression-1-1` before), and later rounds take them in `--kept-finding-ids` and `--dismissed`; a regression has no severity, so it cannot be left as low/advisory. Each verify's signed record now holds the record it chained from (`previousRunId`), its place (`link`), and its `dismissed` reasons and `lowAdvisory` ids, so the open set is computed from signed records only; a fork (two verifies chained from one record), a gap, a link of another review's chain, an unsigned link or a link out of place refuses the chain with "run a new review". The undo guard: a verify after the first is told every id an earlier round resolved (title, file and the verifier's note, as data) and asked whether the new commits touch or undo any of those fixes; a hit is a regression whose `undoes` names that id, shown as `· undoes F-1`. Each verify comment is a short delta and names what is still open (`**Open after this round:** F-2, V1-R1`). A verify no longer posts the close-out card on its own: `verify --close-out` (`closeOut: true`) posts it only when nothing is open after a verify with no lost seat, and says why not otherwise; without it, a verify that leaves nothing open says how to ask for the card. `comment` reads the review's whole verify chain itself and lists every id as resolved (the round of the chain that resolved it, no longer "the earliest round after which every later round agreed"), dismissed, low/advisory, or under `### Open (not resolved)` when the owner stops with ids open (a review finding no round kept reads `not verified`; it used to be refused as outstanding); `--verify-run-id` must name the latest verify. Both cards name lost verify seats on `Lost:`. A review whose verifies were written before this change cannot be chained: verify and comment refuse it with "run a new review", as they did unsigned records. The skill now verifies against the latest verify, passes only open ids, dismisses with reasons, and posts the close-out when the owner says the rounds are done (or with `--close-out` on a verify that leaves nothing open).
- The skill is about 1.2 KB shorter: it no longer repeats what the command's own report and refusals say (the record-key check, how groups are laid out, what each PR comment holds, resume's refusal list).
- A review's reply says why each lost seat was lost, one line per seat under `Lost:` (`- sol/holistic: 401 unauthorized`), cut at 200 characters. The reason was only in `report.md`. The PR comment still names the seats alone.
- The publish workflow installs the packed tarball and runs it (`npm run smoke:installed`) before it publishes, and refuses a tag whose commit is not on `main`. CI and publish use the same action versions.
- Every review lens ends with one shared closing rule, pinned by a test so the copies cannot drift. It now asks for issues the change introduces, including in code it does not touch (it said "in the changed code"), and says what high, medium and low mean: high for lost or corrupted data, a security hole or a broken main path; medium for a wrong result or a failure on a reachable side path; low for the rest. A lens that sets its own severity, as `tests` does, keeps it. The skill states the same scale.
- The `tests` lens prompt is split into paragraphs; its rules are unchanged.
- The skill takes the merge base with the default branch, not with `main`.
- The close-out card is easier to read (T505). Both the automatic `## Review panel · close-out` card and the manual `comment` card now show the findings with their counts by severity (`**4 findings** (4 medium)`), how many were resolved and in how many verify rounds, and leave every zero count out; `Lost:` appears only when a seat was lost, and the dismissed and low/advisory sections only when they have ids. Each kept finding is listed, by severity, as `- **F-1 [medium]** <title> · resolved in verify N`, N the earliest counted round that marked it resolved (every voting seat that answered said resolved) after which every later counted round that answered for it also said resolved; the card never says “fixed”. A round's number is the `verify N` its comment posted as, read only from the review record's signed `round-<N>.posted`, and its seats and dispositions only from its own signed verify record; the card counts its own verify and the posted rounds before it, and a verify that never posted counts as a round with no number (its ids read plain `resolved`), after only the posted rounds reserved before it (by the time in each run id, which `record.mac` binds). `comment` authenticates and uses a supplied `verifyRunId` whenever one is given, even with every finding dismissed or left as low/advisory, and requires one only when ids are left resolved. `**Seats:**` is now `**Review seats:**`, and a new `**Verified by:**` line lists the seats that voted in each counted round once, grouped by lens (a lost verify seat is not named). The range shows the base ref only when it is not itself a commit id, and the head as one short SHA (the commit the verify checked); `comment`'s `head` (`--head`) is still accepted and no longer shown. The range line links to the review comment and the last 10 verify comments (after a `…`) on the same PR when they can be found among its comments (this author, first-line heading, the round's hidden marker as the last line), only at the `html_url` gh gave when it is exactly that PR's comment URL; a comment that cannot be found has no link and the card still posts. The automatic card now reads the PR's comments once, after its claim, for both its duplicate check and its links. Long lists are still cut from the end with the hidden marker last.
- PR comments are easier to read. No run id appears in visible text in any posted body (review, verify, the automatic close-out and the manual `comment` card); each ends with one hidden `<!-- review-panel review=<id> verify=<id> -->` marker holding only ids of the run-id character set, and the close-out duplicate check now matches author, heading and that exact marker as the body's last line (a card posted before this change still counts by the review id on its line 2). The visible commit range stays. Labels the tool writes are bold (`**F-1 [high]**`, `**Evidence:**`, `**Seats:**`, `**Lost:**`, `**F-1 resolved**`); seat text never is. Posted text now escapes only what can form Markdown or HTML (`` \ ` * _ [ ] < > | ~ & ``, `!` before `[`, and block markers at the start of the text), so parentheses, braces, quotes and dots read as typed; `&` stays escaped so an entity cannot decode into `@`, `#` or `://`. Every `$` posts as `<span>$</span>`, which closes a gap that was already there: GitHub runs math on `\$` too, so seat text such as `$\color{white}{…}$` could colour or hide text in a posted comment. The close-out card's `Seats:` line uses the reply's format, `holistic (sol, opus), tests (sol, opus)`, instead of `sol, opus (holistic) · extras: tests`.
- Seat-authored finding text is cleaned before anyone reads it. Finding titles, evidence, file names and prior discard reasons in the review and verify replies, in each review `report.md`, and in the kept-finding data handed to verify seats show control, bidi and invisible characters (zero-width characters, U+FEFF, Unicode tag characters) as U+FFFD, and each run of line breaks and tabs becomes one space, so seat text can no longer reorder a line in a terminal or plant a heading in `report.md`.
- The reply's `Suggest:` block lists only suggested lenses that did not run, one per line with its reason and first evidence, for example `` - security: added line(s) touch auth/crypto/subprocess/deserialization (`src/run/record-key.ts:42`, +2 more) ``. Each file name is a code span with control, line-break, line-separator and invisible format characters (bidi controls, zero-width characters, U+FEFF, Unicode tag characters, variation selectors, Hangul fillers) replaced, so diff content cannot write terminal escapes, hidden text or markdown into a reply. There is no block when every suggested lens ran. When the diff cannot be read (git fails, the diff is over 32 MiB, or it adds over 200,000 lines, bounds that keep the host process's memory safe), `suggest` and the `Suggest:` block say "Suggestions unavailable: the diff could not be read" with the cause, never that no rule matched.
- Replies and reports no longer end with "Not a merge decision." The tool still gives no verdict.
- **Breaking:** pi-review-panel is now a command, not a Pi tool. The npm package `pi-review-panel` publishes the `review-panel` bin, built into `dist/` when the package is packed (never committed), with the Pi SDK (`@earendil-works/pi-coding-agent` 1.5.2) as a pinned dependency instead of a peer. Install it with `npm install -g pi-review-panel`, then `review-panel skill install`. Pi users: run `pi remove npm:pi-review-panel` first, then those two commands. An unedited hand copy of the unreleased `host-skills/review-panel` skill (byte for byte one of the versions this repository shipped), and a link into another npm install of `pi-review-panel` (another prefix, Node version or the npx cache), are replaced by `skill install` without `--force`; an edited copy, or a link into a checkout, needs `--agent <id> --force`. The package's `pi` manifest now lists only `skills`, so `pi install` still loads the skill, but it does not put the command on PATH.

### Removed

- A review no longer reads `discard-ledger.json` from earlier records. Nothing in the package ever wrote that file; it was the reader half of a planned feature (flag a finding near one discarded in an earlier run). The reader took any folder under `.review-panel/runs/` with a `COMPLETE` file, unsigned, so a file planted in the reviewed repository could add "discarded in a prior run" and a reason of its choosing to a finding in `report.md`. The `## Unreadable discard ledgers` section and the `- Flag:` and `- Prior discard reason:` lines are gone from `report.md`.
- **Breaking:** the repository audit is gone (T504). Repository audits moved out of this package; the skill already had none. `review-panel audit` and `call '{"action":"audit"}'` now exit 2 with "audit was removed from review-panel", instead of running. The audit passes and their prompts (`prompts/audit-*.md`), the audit panel planner, the audit report and the unused claim-audit seat role (`submit_audit`) are no longer shipped, and the `passes` argument is gone. `resume` refuses an interrupted audit record left by an earlier version ("audit records can no longer be resumed") before any seat runs; `verify` and `comment` refused audit records already and still do. No owner-config key was audit-only, so an existing `config.json` loads unchanged. What to do: use `review` for a change, and run repository audits with the tool they moved to; delete old audit records under `.review-panel/runs/` when you no longer want them.
- **Breaking:** the `review_panel` Pi tool (`src/tool/review-panel.ts`) and its `typebox` dependency. Every action it offered is a `review-panel` subcommand, and `review-panel call '<json>'` takes the same argument object. The `review-panel-pi` skill and the separate `host-skills/review-panel` skill are replaced by the one `review-panel` skill.
- The `pi-review` host skill, which started Pi from a host agent. Use the `review-panel` skill instead, and delete installed copies under `~/.grok/skills/pi-review`, `~/.codex/skills/pi-review` and `~/.claude/skills/pi-review` (`review-panel skill install` names any it finds).

### Fixed

- `skill install` and `skill uninstall` leave a stamped copy alone when it holds a file the package does not ship, and say to use `--force`. They removed the folder with the user's file in it.
- `review` exits 2 for a badly shaped `--seats`, `--lenses` or `--scoping-note`, as `verify` does and as the exit-code table says. It exited 1, and only after the readiness check had run.
- `diagnose` says what is wrong and what to do. A missing config now gets its path and the example to start from; a relative `PI_REVIEW_PANEL_CONFIG` and a config that cannot be read get their own cause (all three used to get the same "Create the outside-repository config" row). A `defaults.seats` entry that names no roster row is refused as `defaults.seats[n] must name a roster id`; before, `diagnose` passed it as ready and `review` then refused. A login check that fails keeps the provider's reason, the login row gives the command (`review-panel auth login <provider>`), and the model row says to check both ids for a typo.
- An interrupted review keeps a seat that had already submitted. A seat that had called its submit tool but not ended its turn when Ctrl-C arrived was recorded as voted in `execution.json` and got no `seats/<n>.json`, so `resume` ran it, and charged for it, a second time.
- On Windows, a seat can no longer read outside its worktree through a Git Bash / MSYS (`/c/...`), WSL (`/mnt/c/...`) or Cygwin (`/cygdrive/c/...`) drive path. Pi rewrites these to `C:\...` before reading; the seat's path guard did not, so with the worktree at `D:\a\repo` it let `/a/repo/x` through as inside while Pi read `A:\repo\x`. The guard now applies Pi 1.5.2's rewrite in Pi's order, on Windows only, to both the tool path and the worktree.
- The lens-suggestion rules read the diff correctly. An added line that reads `++ b/<anything>` is content, never a file header, so it can no longer rename the evidence or hide the lines after it (`++ b//dev/null`). A file name with a non-ASCII character, a tab, a quote or a backslash is read as written (`core.quotePath=false`, `--name-only -z`, git's quoted `+++ "b/…"` form unquoted), so its added lines are matched and pinned to it. Every file is diffed as text (`--text`), so a NUL byte or a `-diff` attribute in the change's own `.gitattributes` cannot hide its added lines, and a diff over 1 MiB is read in full instead of matching nothing.
- A seat whose provider is registered by one of its own `extraExtensionPaths` extensions (for example `claude-code` from `pi-claude-code`) now runs, and `diagnose` reports it ready. `diagnose` now loads each row's configured extensions and runs the provider's own auth check; it still starts no session and runs no model. Each row's check is bounded at 30 seconds, and a row that does not finish gives a timed-out row naming its extensions. A provider check that throws counts as not authenticated.
- Posted text keeps GitHub math off and its size fixed. A paragraph of nothing but `<span>$</span><span>$</span>…<span>$</span><span>$</span>` still rendered as display math on GitHub, so a zero-width joiner now goes between adjacent dollar spans (checked with `gh api markdown`). Each `$` posts as 14 characters, so a few all-`$` findings could fill the comment budget and push later findings, other seats' highs among them, into the cut count; each text field is now also cut to at most twice its length once escaped (a 300-character title of dollars posts 40 of them), never inside an escape or a dollar span. A group too long to post even its header and first member now ends the list like a plain row, instead of being cut while shorter, lower groups after it still posted, so the rows the footer counts as cut are always the last ones.

## [0.3.0] - 2026-10-26

### Added

- The `tests` lens checks tests a change adds or edits for value: tests that cannot fail, mocks that supply the asserted behavior, duplicates, unreachable inputs, whole-output snapshots, library-behavior tests, trivial-code tests, and test-only production hooks.
- The `tests` lens checks deleted tests: each must leave its contract proven by another named test, unless it was deleted with the production code it covered.
- The `tests` lens and the `tests` audit pass flag tests that are flaky by construction, always as a fix, never a removal.
- The `tests` audit pass tags low-value tests `[action: fix|merge|remove]` and reports merge or remove only with evidence; protected contracts, trust-boundary edge cases, and skipped or disagreeing tests are never removal candidates.
- The review skill documents the audit cleanup loop: audit, cleanup PR, then `review`.

### Changed

- The example config sets `defaults.lenses: ["tests"]`, so the tests lens runs on every review. Each default extra adds up to two seats; drop it to save them.
- A low-value test a change adds is medium only when the seat names the existing test that proves its contract or the guard that makes its input unreachable; otherwise low.
- `tests` is suggested for any source or `.snap` change, with one neutral reason.
- Review results no longer suggest a lens the panel already ran.
