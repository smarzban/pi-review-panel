Audit the repository's tests. Explore the whole pinned tree with read, grep, find, and ls. Report two kinds of defect. First, false confidence: production behavior and critical handoffs whose tests would still pass if the wiring were removed, swapped, or broken, flaky test mechanisms, and meaningful coverage gaps, not a request for more tests in general. Second, tests that cost more than they protect: tests with no real assertion, expected values computed the way the code computes them, lists copied from the source or assertions that search the source text, mocks that supply the asserted behavior, one contract tested at several layers or an old test left beside its replacement, whole-output snapshots used in place of a focused assertion, tests of a library's behavior rather than this code, tests of trivial code with no logic and no production handoff, tests of an input no real caller, spec, or input boundary can produce, and production exports or flags that only tests use. Mark each second-kind finding [action: fix|merge|remove]. A test that passes while the code is broken can be medium or high; every merge or remove candidate is low. Before marking merge or remove, read the full test, the production code it covers, and its callers. Then name the test that still proves the contract, or show that no contract exists; for an unreachable input, name the guard that makes it unreachable; and say what the removal unlocks, if anything. Without that evidence, do not report it. Never mark remove a test that guards a public API, protocol, config, migration, storage, security, or default-value contract, or an edge case reachable at a trust boundary such as user input, parsing, security, or config. You cannot run the suite, so you cannot see which tests fail: never mark remove a test that is skipped, quarantined, marked todo, or whose assertions disagree with the code. Mark it fix, because it may expose a product bug. Slowness alone is not a reason to remove a test. Prefer a few high-confidence candidates to a long list, and never chase deletion counts. For every finding, use the existing Finding schema through submit_findings exactly once. Put the affected area and [effort: quick|medium|large] in the title or evidence. Include a concrete failure scenario and an actual consumer. For a removal candidate, the failure scenario names the regression it lets through, or the specific refactor or simplification, and its file, that it would wrongly turn red, and the consumer is whoever makes that change.
